# L2 · MVP 명세

상태: 작성 중 · 모드: lite · 역할: 제품 분석가 · 입력: L1 체크포인트(6번째 저장) · 마지막 저장: sprint.py save 기록 참고

> **한눈에 보기**
> - **핵심 내용**: Must 기능 13개(친구 화면 6, 주인 화면 2, MCP 도구 5개 묶음), 이번에 넣을 Should 3개(F14·F16·F17), 나중으로 미룬 것 1개(F15). 친구는 이름 + 4자리 PIN으로 자기 신청을 다시 찾는다. 핵심 흐름 3개(친구 신청, AI 일정 등록, AI 신청 처리). 겹침 규칙 하나로 친구 화면과 MCP가 같은 판정을 쓴다.
> - **결정 필요**: 없음. 4개 모두 확정 (맨 아래 "확정한 결정")
> - **다음 행동**: 결정에 답하고 "다음"이라고 하면 빌드 설계(L3) 작성

## 지금은 어떻게 하나 (3줄)
- 친구가 메신저로 "언제 돼?"라고 묻고, 나는 내 일정을 확인해 가능한 날을 하나씩 답한다.
- 여러 친구와 동시에 이야기하면 같은 날을 두 사람에게 주는 일이 생길 수 있다. (가정: 사용자 말에서 추론, 실제 빈도는 확인 안 함)
- 내 일정은 이미 다른 곳(머릿속, 다른 캘린더)에 있어서 또 입력하는 것이 번거롭다. 그래서 AI가 대신 입력한다.

## 핵심 사용자 흐름

**흐름 A · 친구가 약속 신청**
친구 → `meet.keyda.site` 접속 → 월간 캘린더에서 빈 날짜 클릭 → 버튼 6개 중 하나 선택(또는 "직접 선택"으로 시작·끝 시간 지정) → 이름·PIN 4자리·메모 입력 후 신청 → "신청 중" 확인 화면. 다시 오면 "내 신청"에서 상태(신청 중·확정·거절·취소)를 본다. 같은 브라우저면 바로 보이고, 다른 기기에서는 이름과 PIN을 넣으면 보인다. "신청 중"인 건 거기서 취소할 수 있다.

**흐름 B · AI가 내 일정 등록**
나 → Grok에게 "다음 주 화·목 19시부터 22시 회의" → Grok이 MCP 도구로 불가능 시간 등록 → 이미 신청이 걸려 있던 시간이면 Grok이 겹치는 신청을 알려 줌 → 친구 화면에서 해당 시간이 "불가"로 바뀜.

**흐름 C · AI가 신청 처리**
나 → Grok에게 "새 약속 들어온 거 있어?" → Grok이 신청 목록을 읽어 날짜·시간대·이름·메모를 알려 줌 → "민지 건 수락, 나머지는 거절" → Grok이 수락·거절 → 친구 화면에서 "확정"으로 보이거나 칸이 다시 열림.

## 겹침 규칙 (모든 기능이 같이 씀)
| 규칙 | 내용 |
| --- | --- |
| 시간 기준 | 한국 시간(Asia/Seoul) 고정. 시간 구간은 시작 포함·끝 제외. 예: 11:30–14:00과 14:00–18:00은 겹치지 않음 |
| 막는 것 | 불가능 시간, "신청 중" 신청, "확정" 신청 |
| 막지 않는 것 | "거절", "취소"된 신청 |
| 하루에 여러 약속 | 시간이 안 겹치면 가능. 예: 점심은 A, 저녁은 B |
| 먼저 신청한 사람 우선 | 두 친구가 거의 동시에 같은 시간을 신청하면 먼저 저장된 신청만 성공하고, 나중 사람에게는 "방금 다른 신청이 들어왔어요"라고 안내 |
| 신청 가능 기간 | 내일부터 90일 뒤까지. 오늘과 지난 날짜는 고를 수 없음 |
| 직접 선택 | 30분 단위, 최소 30분, 같은 날 안에서만(00:00–24:00) |
| 내 일정 등록과 겹침 | 불가능 시간은 신청과 겹쳐도 등록됨(내 일정이 우선). 대신 겹친 신청 목록을 돌려줘서 AI가 나에게 알림 |

| F05 | 같은 시간에 동시 신청이 오면 나중 사람은 실패 안내를 받는다 | Must | A | 같은 시간으로 두 번 연속 신청 요청 시 두 번째가 거절되는 테스트 통과 |

## 품질 3가지
| 항목 | 기준 |
| --- | --- |
| 체감 속도 | 캘린더 첫 화면이 1초 안에 보인다. 버튼을 누르면 바로 반응하고, 저장 중에는 버튼에 "저장 중" 표시 |
| 오류 안내 | 신청 실패 시 빈 화면 대신 이유와 "다시 시도" 버튼. 서버가 꺼져 있으면 "잠시 후 다시 시도해 주세요" |
| 비밀 보호 | PIN은 해시로만 저장하고, 틀린 PIN을 5번 넣으면 그 이름으로는 10분간 조회·취소를 막는다(4자리는 경우의 수가 1만 개뿐이라 마구 넣어 보는 것을 막기 위함). 비밀 키는 서버 환경 변수에만 둔다. 공개 저장소·화면·주소창(URL)에 넣지 않는다. 주인 화면은 키를 브라우저에만 기억하고 요청 헤더로 보낸다. 친구용 응답에서는 일정 제목·이름·메모를 서버에서 미리 지운다 |

## 가정과 확인 필요
| 항목 | 내용 | 확인 방법 |
| --- | --- | --- |
| Grok이 먼저 알려 주기 | MCP는 AI가 물어볼 때 답하는 구조다. 새 신청이 들어왔을 때 Grok이 먼저 말을 거는 것은 이 범위로는 안 된다. "양방향"은 AI가 읽고 쓰기를 모두 한다는 뜻으로 잡았다 | 결정 3 |
| Grok의 MCP 연결 형식 | Grok이 지원하는 원격 MCP 전송 방식(Streamable HTTP 등)과 Bearer 헤더 지원을 사용자가 알려 준 설명대로 가정함 | 개발 중 실제 연결로 확인 |
| 친구 신원 | 로그인이 없어 누구나 아무 이름으로 신청할 수 있다. 내가 수락할 때 걸러낸다. 이름 + PIN은 "내 신청 다시 찾기"용이지 본인 인증은 아니다. 같은 이름이라도 PIN이 다르면 다른 사람으로 본다 | 장난 신청이 많아지면 그때 대책 |
| PIN 분실 | 친구가 PIN을 잊으면 스스로 취소할 수 없다. 나에게 말하면 내가 Grok이나 주인 화면으로 처리한다 | - |
| 시간대 | 모든 사용자가 한국 시간에 있다고 가정 | - |
